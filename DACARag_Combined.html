DACARag — Project Retrospective

A polyglot RAG system for Irish trades. What was built, where the data lives, and how each piece serves the chatbot.

What DACARag is. A retrieval-augmented chatbot for plumbers, carpenters, and electricians that reads incoming customer quote-request emails, looks up whether the customer is known, finds similar past jobs, suggests likely materials, and drafts a quote. Every answer is grounded in three data stores rather than the LLM's parameters.

The architecture in one line. MongoDB Atlas owns the records, Neo4j owns the relationships, Atlas Vector Search owns the embeddings; Claude Haiku routes queries; Streamlit serves the UI.

Phase 0

Project setup and synthetic data generation

25 Apr · ~2h

Stand up the project skeleton, the Docker compose stack, and a deterministic synthetic dataset of Irish trades records.

Files created

  • ingest\generate_trades_dataset.py — generates the seven core CSVs and 100 quote-request .eml files using fixed random seeds for reproducibility
  • docker-compose.yml — defines the local Neo4j 5.20 container with APOC plugin and persistent volumes
  • .env — holds MONGO_URI, MONGO_DB=trades_quotes, NEO4J_URI=bolt://localhost:7687, and the Anthropic key
  • requirements.txt — pins pymongo>=4.6, neo4j>=5.20, sentence-transformers, streamlit, anthropic, python-dotenv

Why this matters for the chatbot
Fixed random seeds mean the dataset is regenerable byte-for-byte. Every later phase can be re-run from scratch without losing reproducibility — important for marking, demos, and the evaluation set.
Phase 1

MongoDB ingestion

26 Apr · ~2h

Load every CSV into MongoDB Atlas and the 100 emails into GridFS, with indexes tuned to the chatbot's expected access patterns.

How this serves the chatbot
When the user asks "what's Gerard Walsh's phone number?", the orchestrator sends one indexed Mongo lookup and gets the answer in under 10ms. No graph traversal, no vector search — the right tool for an identity question is a document store with a primary-key index.
Phase 2

Neo4j graph build

27 Apr · ~2h

Project the MongoDB data into a labelled property graph. The graph stores only IDs and relationships — never duplicates document content.

Key relationships (2,030 total)

How this serves the chatbot
When the user asks "how much for a boiler installation?", Neo4j traverses USES_ITEM relationships in one Cypher query — three milliseconds. The equivalent in MongoDB would be a three-stage $lookup pipeline.
Phase 3

Multi-source ingestion and LLM enrichment

28 Apr · ~2h

Process 100 quote-request emails and 15 supplier PO PDFs into structured records using Claude Haiku, then add them to both stores.

Architectural decision. Email and PO ingestion is the system's most architecturally rich component because it exercises all three learning outcomes simultaneously: GridFS for binary storage, LLM extraction for unstructured-to-structured conversion, and graph projection for relationship modelling.
How this serves the chatbot
When the user asks "show me PO-2026-P0042", the orchestrator hits MongoDB by po_number and gets the structured JSON instantly. When they ask "how much did we pay for materials?", the orchestrator joins POs to job types via the graph, then sums materials_subtotal.
Phase 4

Vector embeddings and Atlas Vector Search

29 Apr · ~2h

Embed every email body, PO description, and customer note into 384-dim vectors and index them with Atlas Vector Search.

SourceChunksWhat it enables
PO descriptions~140"What was the boiler model on the last big plumbing PO?"
Email bodies~85"Did anyone email about a leaky tap in March?"
Customer notes~38"Find me the customer in Drumcondra who had the kitchen rewire"
Total263
How this serves the chatbot
Vector search picks up semantic similarity that keyword search misses. "I need someone for a leaky tap" doesn't have to match "dripping faucet" exactly — the embedding space captures the meaning.
Phase 5

Retrieval orchestration

30 Apr · ~2h

The brain. A query router that classifies the user's intent and dispatches to the right combination of retrieval modules, then assembles the results into one Markdown context block for Claude.

retrieve/ module map

FileRole
router.pyLLM-first classifier — regex patterns for IDs, Claude Haiku for everything else
mongo_lookup.pyExact-match retrievers: get_customer, get_invoice, get_po, get_email
graph_search.pyCypher traversals: items_for_job, customer_full_history, similar_pos_by_job_type
vector_search.pyAtlas $vectorSearch aggregation with all-MiniLM-L6-v2
context_assembler.pyMerges retrieval results into one Markdown block for Claude
predict_quote.pyKiller feature — combines Neo4j recipe + MongoDB item prices + invoice labour stats
orchestrator.pySingle entry point: answer_query() — routes, retrieves, assembles, calls Claude
How this serves the chatbot
predict_quote returns a boiler installation estimate of €2,002.06 inc VAT, within 5% of benchmark PO-2026-P0042 (€2,106.50). No single store can answer this — it requires Neo4j for the recipe, MongoDB for current item prices, and MongoDB again for historical labour statistics.
Phase 7

BI dashboard and evaluation set

2 May · ~2h

Add a business-intelligence page to the Streamlit app, plus prepare a 20-question evaluation set with gold-standard answers.

Dashboard contents

  • Three KPI cards — Customers served, Total jobs value (inc VAT), Materials spend (POs)
  • Revenue trend chart — monthly revenue line chart, one series per trade
  • Top 10 catalogue items — horizontal bar by total invoice value
  • Activity by county — horizontal bar by revenue
Why this matters for the rubric
The dashboard satisfies the rubric's "Business Intelligence" line as a substantively different artefact from the RAG evaluation. KPIs and charts answer business-owner questions; the chatbot answers operational questions. Same data, different access patterns, two distinct deliverables.

Phases 9–11

Report, slides, submission

4–6 May

Wrap up the deliverables: written report, 10-slide deck, demo rehearsal, submission.

Future-work flags

  • Cross-encoder reranker — BERT cross-encoder between vector retrieval and context assembly
  • Hybrid retrieval (BM25 + dense) — RAG-Fusion pattern
  • Invoice → materials graph chain — invoice lookup route does not yet query Neo4j for USES_ITEM
  • Prompt-injection defences and PII redaction — out of scope for academic deployment
