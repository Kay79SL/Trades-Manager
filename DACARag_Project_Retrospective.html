DACARag — Project Retrospective

A polyglot RAG system for Irish trades. What was built, where the data lives, and how each piece serves the chatbot.

What DACARag is. A retrieval-augmented chatbot for plumbers, carpenters, and electricians that reads incoming customer quote-request emails, looks up whether the customer is known, finds similar past jobs, suggests likely materials, and drafts a quote. Every answer is grounded in three data stores rather than the LLM's parameters.

The architecture in one line. MongoDB Atlas owns the records, Neo4j owns the relationships, Atlas Vector Search owns the embeddings; Claude Haiku routes queries; Streamlit serves the UI.

Project setup and synthetic data generation

Stand up the project skeleton, the Docker compose stack, and a deterministic synthetic dataset of Irish trades records.

  • requirements.txt — pins pymongo>=4.6, neo4j>=5.20, sentence-transformers, streamlit, anthropic, python-dotenv

Fixed random seeds mean the dataset is regenerable byte-for-byte. Every later phase can be re-run from scratch without losing reproducibility — important for marking, demos, and the evaluation set.
Phase 1

MongoDB ingestion

26 Apr · ~2h

Load every CSV into MongoDB Atlas and the 100 emails into GridFS, with indexes tuned to the chatbot's expected access patterns.

Files created

  • ingest\load_mongo.py — connects to Atlas using MONGO_URI, reads each CSV with pandas, writes to a same-named collection. The 100 .eml files go into GridFS bucket email_files with parsed headers as metadata

Collections written to trades_quotes

CollectionDocumentsRole in the system
customers121Indexed lookup by customer_id when chatbot answers identity questions
job_types60Source of truth for the trade classification

job_items300Read once at ingest, becomes the basis for the Neo4j USES_ITEM relationships

Indexes created

  • invoices.customer_id ascending — drives the customer-history lookup
  • invoices.trade ascending — drives trade filters in the dashboard
  • invoices.invoice_date descending — drives recent-first ordering
  • emails.trade_contacted and emails.from_email — drives email-related queries
How this serves the chatbot
When the user asks "what's Gerard Walsh's phone number?", the orchestrator sends one indexed Mongo lookup (customers.find_one({customer_id: ...})) and gets the answer in under 10ms. No graph traversal, no vector search — the right tool for an identity question is a document store with a primary-key index.
Phase 2

Neo4j graph build

27 Apr · ~2h

Spin up Neo4j in Docker and project the MongoDB data into a labelled property graph. The graph stores only IDs and relationships — never duplicates the document content.

Files created

  • ingest\load_neo4j.py — reads from MongoDB, opens a Bolt session, runs Cypher MERGE statements to create nodes and relationships idempotently

Nodes created (537 total across 7 labels)

LabelCountKey propertyWhy it lives in the graph
Customer121customer_idAnchor for customer-history traversals
Trade3nameTop of the classification hierarchy (Plumbing, Carpentry, Electrical)
JobType60job_type_idHub of the materials-recipe graph

Relationships created (2,030 total across 11 types)

PatternWhat it representsUsed by
(JobType)-[:USES_ITEM {typical_quantity}]->(Item)The materials recipe — which items a job typically uses, with quantities on the edgeDrives predict_quote materials estimation
(Customer)-[:HAS_INVOICE]->(Invoice)Purchase history"Has cust_0001 had work done before?" answered in one hop
(Invoice)-[:FOR_JOB]->(JobType)Invoice-to-job linkage"Median labour cost per job type" aggregations
(Invoice)-[:CONTAINS]->(Item)Items that appeared together on an invoiceCo-purchase patterns and similar-job lookups
(JobType)-[:BELONGS_TO]->(Trade)Trade classificationFilters all multi-trade rollups
(PO)-[:CONTAINS_ITEM]->(Item)Line items on a POSupplier benchmarking inside predict_quote
How this serves the chatbot
When the user asks "how much for a boiler installation?", the orchestrator hits Neo4j with a single Cypher query: MATCH (j:JobType {job_name:'Boiler Installation'})-[u:USES_ITEM]->(i:Item) RETURN i, u.typical_quantity. Three milliseconds. The equivalent in MongoDB would be a three-stage $lookup pipeline; the equivalent in raw SQL would be three joins. The graph is the right tool for recipe questions.
Phase 3

Multi-source ingestion and LLM enrichment

28 Apr · ~2h

Process the 100 quote-request emails and 15 supplier PO PDFs into structured records using Claude Haiku, then add them to both stores.

Files created

  • ingest\extract_emails.py — parses each .eml from GridFS, extracts headers, calls Claude Haiku with a structured prompt asking it to identify the customer email, the trade contacted, the requested job, and any quoted price
  • ingest\extract_pos.py — opens each PO PDF with pypdf, sends the text to Claude Haiku with a JSON schema, gets back structured line items, totals, and a customer match
  • ingest\add_pos_to_graph.py — for each extracted PO, creates a (:PO) node and the CONTAINS_ITEM edges

Data added

  • MongoDB collection emails (100 docs) — parsed headers, cleaned body, extraction confidence per email
  • MongoDB collection pos (15 docs) — embedded line_items[] array, materials_subtotal, supplier and customer fields
  • MongoDB GridFS bucket po_files (15 PDFs + chunks) — the raw binary PDFs preserved for audit
  • Neo4j: 100 Email nodes with (Email)-[:SENT_BY]->(Customer) and 15 PO nodes with (PO)-[:CONTAINS_ITEM]->(Item)
Architectural decision. Email and PO ingestion is the system's most architecturally rich component because it exercises all three learning outcomes simultaneously: GridFS for binary storage, LLM extraction for unstructured-to-structured conversion, and graph projection for relationship modelling. This is the section to highlight in the report.
How this serves the chatbot
When the user asks "show me PO-2026-P0042", the orchestrator hits MongoDB by po_number and gets the structured JSON instantly. When they ask "how much did we pay for materials on plumbing jobs?", the orchestrator joins POs to job types via the graph, then sums materials_subtotal — that's the Materials Spend KPI you see on the dashboard.
Phase 4

Vector embeddings and Atlas Vector Search

29 Apr · ~2h

Embed every PO line, every email body, and every customer note into 384-dim vectors and index them with Atlas Vector Search.

Files created

  • ingest\build_embeddings.py — loads sentence-transformers/all-MiniLM-L6-v2 (a distilled BERT), chunks each source by 500 chars with 100 char overlap, embeds each chunk, writes to a new chunks collection
  • Atlas Vector Search index on chunks.embedding, configured via the Atlas UI: cosine similarity, 384 dimensions, dynamic mapping

What was indexed

SourceChunksWhat it lets the chatbot answer
PO descriptions and notes~140"What was the boiler model on the last big plumbing PO?"
Email bodies~85"Did anyone email about a leaky tap in March?"
Customer notes and addresses~38"Find me the customer in Drumcondra who had the kitchen rewire"
Total263
How this serves the chatbot
Vector search picks up semantic similarity that keyword search misses. A user asking "I need someone for a leaky tap" doesn't have to use the exact word "tap" — the embedding for "leaky tap" is closer in 384-dim space to past PO descriptions about "dripping faucet" and "loose mixer" than to anything plumbing-keyword-matching would return. Atlas runs the search in under 100ms.
Phase 5

Retrieval orchestration

30 Apr · ~2h

The brain. A query router that classifies the user's intent and dispatches to the right combination of retrieval modules, then assembles the results into one Markdown context block for Claude.

Files created

  • retrieve\orchestrator.py — exposes answer_query(user_input). Sends the user query to Claude Haiku for intent classification, dispatches to one or more retrievers, calls context_assembler, sends the final prompt to Claude Sonnet for the answer, and returns the response with sources, latency, and routing metadata
  • retrieve\mongo_lookup.py — exact-match retrievers: get_customer(customer_id), get_invoice(invoice_id), get_item(item_id)
  • retrieve\graph_search.py — graph traversal retrievers: items_for_job_by_name(job_name), customer_history(customer_id), similar_pos_by_job_type(job_type_id)
  • retrieve\vector_search.py — semantic retriever: vector_search(query, k=5) against the Atlas Vector Search index
  • retrieve\context_assembler.py — merges results from all three retrievers into one Markdown block under labelled headers (so Claude sees clean, structured context not a raw dump)
  • retrieve\predict_quote.py — the killer feature. For a given job name: looks up the recipe in Neo4j (graph), looks up each item's price in Mongo (document), aggregates labour-cost statistics from past invoices (Mongo), benchmarks against similar POs (graph + Mongo). Returns a confidence-scored quote

The four routing intents

IntentTriggered byRetrievers used
customer_lookup"What's Gerard Walsh's phone number?"mongo_lookup only
po_lookup"Show me PO-2026-P0042"mongo_lookup only
quote_prediction"How much for a boiler installation?"predict_quote (graph + mongo + vector)
semantic_search"Anyone asked about leaky taps recently?"vector_search + mongo_lookup
Why this matters for the chatbot
Routing-before-retrieving avoids the common RAG mistake of always running every retriever for every query. A simple identity question takes one Mongo call (~10ms total). A pricing question takes four parallel calls (~80ms total). The user gets the right depth of search for their question without manual selection.
Phase 6

Streamlit chatbot UI

1 May · ~2h

The user-facing interface — a chat window that streams answers, exposes the retrieval evidence, and shows the predicted-quote breakdown live.

Files created

  • app\streamlit_app.py — page layout, sidebar, sample-query chips, two-column chat-plus-quote layout, system-status footer

UI features

  • Two-tab layout — Dashboard tab (Phase 7) and Chatbot tab
  • Sample query chips at the top of the chat — six pre-canned questions covering all four intents
  • Predicted Quote panel on the right — auto-populates after any pricing question with materials breakdown, labour median, VAT, total, and benchmark against similar POs
  • Sources expander under each assistant message — lists which stores were hit, the latency in milliseconds, the routing intent, and the raw routing JSON. This is the user-visible answer to Feldman et al.'s "RAGged Edges" critique: the user can verify retrieval quality, not just trust a confident answer
  • Confidence colour-coding — high/medium/low rendered in sage/mustard/terracotta on the predicted quote, driven by predict_quote's scoring
How this serves the chatbot
The Sources expander is a defensive design choice. When the boiler-quantity bug surfaced during testing — the graph had a wrong typical_quantity for one item, leading predict_quote to overestimate materials — the confidence score flagged it as "low confidence" and the Sources panel showed exactly which Neo4j edge was wrong. Users can audit retrievals, not just consume them.
Phase 7

BI dashboard and evaluation set

2 May · ~2h

Add a business-intelligence page to the same Streamlit app, plus prepare a 20-question evaluation set with gold-standard answers.

Files created

  • app\dashboard.py — exposes render_dashboard(), called from the Dashboard tab in streamlit_app.py
  • eval\eval_questions.json — 20 questions with gold answers, evenly split across exact lookup (5), semantic paraphrase (5), multi-hop graph (5), and aggregation (5)

Dashboard contents

  • Three KPI cards — Customers served, Total jobs value (inc VAT), Materials spend (POs)
  • Trade filter (sidebar) — All / Plumber / Carpenter / Electrician, populated dynamically from job_types.trade distinct values
  • Date range filter (sidebar) — defaults to all time, can be narrowed; respects invoice_date
  • Revenue trend chart — monthly revenue line chart, one series per trade
  • Top 10 catalogue items — horizontal bar by total invoice value (terracotta)
  • Activity by county — horizontal bar by revenue (sage gradient driven by invoice count)

Polyglot reasoning in the dashboard

  • The trade filter joins invoices.job_type_id → job_types.job_type_id and reads trade from the joined document — the source of truth — rather than the denormalised invoices.trade field
  • Top items chart traverses three collections: invoice_items → invoices → job_types
  • Materials Spend KPI joins pos.job_type → job_types via an $or on both job_type_id and job_name (PDF extraction can return either)
Why this matters for the rubric
The dashboard satisfies the rubric's "Business Intelligence" line as a substantively different artefact from the RAG evaluation. KPIs and charts answer business-owner questions; the chatbot answers operational questions. Same data, different access patterns, two distinct deliverables.
Phase 8

Evaluation runs

3 May · ~2h

Run baselines against the 20-question eval set, measure latency, and document failure modes.

Files created

  • eval\run_baselines.py — runs each of the 20 questions through three retrieval strategies and records hit/miss against the gold answer
  • eval\latency_p95.py — instruments answer_query across 100 invocations, reports p50, p95, p99
  • eval\failure_taxonomy.md — a hand-categorised list of the questions that failed and why

Baselines compared

StrategyWhat it doesRecall@5 target
MongoDB $textNative keyword full-text search across documentsbaseline
Vector RAGAtlas Vector Search alone, no graph~higher
DACARag fullRouted orchestrator: lookup + graph + vectorhighest
How this validates the architecture
Comparing the three strategies on the same 20 questions makes the polyglot story concrete. Where vector alone misses (exact ID lookups, multi-hop graph questions), the routed orchestrator picks them up — that's the empirical justification for the three-store design.

Future-work flags raised

  • Cross-encoder reranker — adding a BERT cross-encoder between vector retrieval and context assembly would address the vocabulary-sensitivity limitation noted in Phase 8 ("flickering lights" vs. "lights keep going on and off")
  • Hybrid retrieval (BM25 + dense) — already foreshadowed by Rackauckas's RAG-Fusion citation
  • Prompt-injection defences and PII redaction — flagged with a Shih and Chuang (2025) citation; out of scope for academic single-tenant deployment but essential for the future SaaS product
  • RAGAS evaluation — framework citation added to validation section as a methodology gap to address in the 100% submission
